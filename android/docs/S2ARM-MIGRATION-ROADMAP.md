# 暗黑 3：S2Arm 代码迁移与功耗优化路线图

编制日期：2026-11-11。本文定义实施顺序、代码边界和验收门槛，不代表相关功能已经实现或通过实测。执行状态统一记录在 [Android STATUS](STATUS.md)；架构事实、构建入口分别见 [ARCHITECTURE](ARCHITECTURE.md)、[BUILD](BUILD.md)。不另建逐轮交接和重复进度表。

## 1. 目标、编号与交付范围

主目标是在 vivo X200 Pro / V2405A / Mali-G925 上，提高 Android《暗黑破坏神 3》的持续运行能效，最终同时达到：正确世界画面与原生 UI、持续原生 60 FPS、整机电池侧平均功耗 ≤4.5 W。帧率和功耗的具体判据见第 8 节。

本路线只针对暗黑 3；保留现有游戏核心、触控、音频、存档、内容和系统服务，主要迁移 S2Arm 的 NVN→Vulkan 图形路径。Windows 可复用部分图形代码和优化方法，独立适配、独立验收，见第 10 节。Android 的 4.5 W 目标不套用于 Windows。

用户所指的“1—5”固定映射如下，后续用编号关联测试和变更，避免编号漂移：

| 编号 | 工作 | 主要目标 |
| --- | --- | --- |
| M | S2Arm NVN→Vulkan 代码迁移 | 减少 Maxwell 命令处理和资源识别开销，建立暗黑 3 专用图形后端 |
| T1 | 精确写入跟踪，减少全量扫描 | 减少 CPU、内存访问、写故障和页面保护成本 |
| T2 | Android ADPF 帧时提示 | 按关键线程的真实工作量和帧预算改善调度 |
| T3 | 减少 GPU 像素与图像搬运 | 降低场景片段执行、附件存取和中间复制负荷 |
| T4 | 队列背压、批量提交、缓冲复用 | 减少重复分配、绑定、上传、提交及无用排队 |
| T5 | 着色器与管线预热 | 减少游戏中首遇编译、卡顿和 CPU 峰值 |

菜单降帧属于后续可选产品策略，不计入本次 T1—T5，也不能用来代替战斗 60 FPS 验收。帧生成、换包名触发 OEM 功能、全面替换系统服务、多游戏启动器不在本次交付范围。

## 2. 起点与必须补齐的证据

### 2.1 可以作为起点的事实

- 当前 Android 已直接执行 ARM64 guest；S2Arm 的“没有 CPU 模拟器”不是本项目新增收益。差异重点在图形入口、资源管理和具体调用成本。
- 留存 S2Arm APK、账本、日志、截图位于 out/android/s2arm/。APK SHA-256 已实算并与账本一致，为 fa6ae5a5fd8e29ee32e9650ae78dcd6f5b0467848ce1e18b0236880adfed7e44；包名 org.s2arm.game.t01001b300b9be000，游戏版本 2.7.7.92380。
- 截图包含暗黑 3 世界场景与 HUD；用户明确确认当时选择了 NVN 直连。这证明已有进世界的原型，不证明持续帧率、完整正确性或节电。
- 留存源码 out/research/S2Arm/ 为 3584904a17d86886bb0346ded50fea1997ee23a4；另已查阅上游 dadb916f3aabab983c7ea1a1b641c2c6b0adcd60。APK 账本未把源码提交与产物建立可复现构建绑定，两者不能直接视作同一构建证明。
- 留存构建启用了 nvn_vk 后端，但离线 LibPack 跳过、未提供 S2A_VULKAN_PROFILE；账本中只有直连图形描述符，没有离线 shader 包。不能套用 Apple 平台的预编译收益。
- 现有 Android 一次带诊断的拔线短窗约为 45.94 composite FPS / 6.674 W；不是长时战斗的正式基线。该窗每轮平均扫描 37281 页、87 页变化、10.579 ms，仅用于说明调查方向。

### 2.2 M0 必须解决的问题

1. 对当前实际安装重新核对 APK、SO、签名、guest BuildID、内容和存档身份；历史安装 SHA 不作为当前事实。
2. 确认留存 S2Arm 包及资源能否恢复测试。先盘点现有材料，再从 local/ 或合法原始输入重建必需内容；不因为旧环境已删而盲目恢复整个 WSL/Docker 工具链。
3. 检查可用签名。S2Arm 旧私钥若不可恢复，保留旧 APK 的测试身份；新构建使用独立验证身份，不卸载或清数据绕过签名和安装确认。
4. 冻结两套对照：A 为当前正确出图的 D3/Eden 基线；S 为留存或可复现重建的 S2Arm NVN 直连包。只有游戏、内部尺寸、场景和设备条件对齐后才做路线能效比较。
5. 先在同条件下测 A/A 噪声，再测 A/S/A。S 若不能稳定出正确画面，先修正确性；若能效没有优势，记录结果并重新判断 M 的投入，T1/T2 仍可独立推进。

## 3. 目标架构与代码迁移边界

### 3.1 后端选择原则

保留一份 D3 guest 和现有 host，冷启动时选择 Eden 或 NVN 后端。一次会话只初始化、呈现一套图形后端；不得在同一帧混用两个后端，或让“直连模式”仍悄悄执行整套 Eden GPU 工作。接入失败应明确报错并允许下一次冷启动回退 Eden。

NVN 路径为：D3 guest → 经校验的 NVN 入口与 ABI 桥 → NVN 语义/命令记录 → Vulkan 资源、shader、提交和同步 → 平台 Surface/窗口 → 显示。

现有 Horizon 服务、存档、内容、音频、输入继续由 D3 host 提供。NVN 的 Window/Queue/Present 与现有显示服务如何衔接必须明确，避免重复提交和重复计帧。

### 3.2 来源与接入清单

以下为已查阅的生产代码入口；依赖闭包仍需在 M1 通过真实构建确认。不能把名称相近的独立测试适配器当作完整生产后端。

| S2Arm 来源 | 迁移内容 | 本项目接入点与注意事项 |
| --- | --- | --- |
| graphics/nvn/gfx/nvn/hle_nvn.c 及同目录的类型、名字表、记录结构 | 暗黑 3 使用的 NVN API、对象和命令语义 | android/host/d3_host.c 的 load_guest / install_guest_hooks；新增经验证的 BootstrapLoader 和返回函数指针桥 |
| graphics/nvn/gfx/nvn/nvn_dirty.c、纹理/池相关实现 | 资源写入通知、页保护、映射代次 | 与现有信号链、内存区域互斥、别名映射和 CPU/GPU 写入跟踪统一；对应 T1 |
| android/native/nvn/mtl_vk_shim.c、mtl_vk_adapter.c、nvn_vk_* | 生产 Vulkan 记录回放、资源、队列、同步与呈现 | 对接 GPU bridge、JNI/Surface、驱动加载；这里的 mtl 名称不表示使用 Metal |

### 3.3 建议的源码落地形式

以下目录和开关均为设计建议，尚未实现，不是现有可执行接口：

- shared/d3-nvn/upstream/：需要跟踪的 S2Arm 原始模块快照、LICENSE/NOTICE 和第三方声明。只收本次必需闭包，不复制整个应用。
- shared/d3-nvn/：暗黑 3 使用的公共类型、记录和资源状态逻辑；是否能跨 Windows/Android 直接编译要逐模块验证，不能因为是 C 就认定已可移植。
- android/gpu/nvn/：Android 的 ABI、线程/信号、Surface、驱动与编译接口适配。平台行为不塞进公共算法层。
- 源码清单记录上游仓库、精确提交、每个文件的原始 SHA-256、本地补丁及许可。修改上游代码保留清晰差异；不只把可执行版本放在会被清理的 out/ 中。
- 为后端、T1、T2、T3、T4、T5 设独立实验开关和配置回执，记录实际生效值；现有开关继续沿用现有语义。新增选项必须同步进入构建/运行说明。

当前 guest 是保留的 ELF；S2Arm 使用 main/sdk.patched.bin 和 android-sp-safe-v1 fixup/gate。不得直接替换 guest 或 SO。函数调用、TLS、x18、栈和回调边界需要按当前 guest 重新实现并测试。

shader 编译依赖是早期决策点：优先验证能否抽取 S2Arm 的编译接口和最小 NativeAOT 闭包；若必须连入大量系统服务，再比较复用现有 Eden shader compiler 的适配成本。M1 结束时选定一条路线并写明输入、输出和依赖，不同时维护两套未完成方案。

建议实施顺序：M0 → M1；在现有 Eden 基线上先串行验证 T1，再验证 T2；随后完成 M2—M5，再对 NVN 后端重测 T1/T2，并依采样推进 T3/T4/T5，最后进入 M6/M7。M4 必需的运行时 shader 编译先做，完整预热属于 T5。

这里允许代码工作交错，不表示允许并发游戏、并发 Frida attach 或并发设备采样。T1 在 Eden 上的改善不能直接计作 NVN 后端的额外收益，两条路径需要分别建立计数和对照。

## 5. S2Arm 迁移的具体工作包

### M1：先证明最小生产闭包可构建

1. 从 Android 的实际生产构建列表追踪 NVN 前端、Vulkan 后端、编译接口的强/弱符号与宏；区分生产实现、测试宿主和空实现。
2. 审计 Apple/POSIX/Android 依赖、汇编和数据布局；不能将原来的 thunk、xstack 或 host shim 原样套进 D3。
3. 接入现有 build_android_profile.py、GPU/host 构建流程，输出仍在 out/android/。Eden 后端继续可构建和回退。
4. 固定 shader 编译闭包，避免为了图形翻译带入另一整套系统服务。产物缺依赖时明确失败，不以空 shader、跳 draw 或返回成功掩盖缺口。
5. 保留本项目 guest 原件、签名和存档；记录 APK 内实际链接模块，不以“某库被映射”代替 dispatch 路径证明。

验收：干净来源加锁定补丁能够重建；APK/SO/签名可核对；两后端分别构建；基础清屏/资源探针通过只记为构建与探针通过，不记为暗黑 3 完成。

### M2：NVN 入口和 ABI

1. 用实际 guest 的 BuildID、布局和指令定位 nvnBootstrapLoader 及必要的内部入口；已有 SDK 符号表只作定位线索。
2. 对游戏后续获得的每个 NVN 函数指针提供正确桥接。覆盖整数、浮点、指针、结构体及栈参数、返回值和 host→guest 回调；检查线程切换与重入。
3. 保持 guest/host TLS、x18、栈对齐与 host 信号处理链正确；禁止把需要包装的 host 裸函数指针交回 guest。
4. 未支持 API 记录名字和上下文，给出明确失败；功能覆盖不能用“查表返回非空”替代。
5. 冷启动回执记录选择结果；NVN 模式证明游戏 draw/submit/present 实际进入目标后端，Eden GPU 执行路径没有同时运行。

验收：有意义的 ABI/回调探针及错误路径通过；连续进入菜单和世界不出现 TLS、栈或异常链回归；错误 BuildID 拒绝写入且未留下部分补丁。

### M3：内存、资源和同步

- 统一注册/撤销内存池、别名与映射代次；处理地址重用，避免旧资源在新映射上继续命中。
- 明确 CPU 写、GPU 写、上传、回读、view 和子资源的所有权/可见性。动态 uniform/顶点数据不能因为地址没变而误判未更新。
- 页保护与故障处理必须覆盖首次布防的 Busy/Active 窗口；共享页面、映射撤销和非 guest 故障不能被吞掉。
- queue/event/counter/fence 的完成必须对应实际提交和内存可见性；未执行的提交不得发布完成。资源只有在引用它的 GPU 工作完成后才能回收。
- 验证超时、OOM、编译失败、Surface 销毁和设备丢失的退出清理；不能靠泄漏所有资源避开寿命问题。

验收：主机/ARM64 资源与同步测试通过；场景切换、动态纹理、特效和物品栏无陈旧内容；验证层阶段没有新增 VUID/SYNC 错误；独立 depth/stencil 和回读检查通过后，再做真实游戏画面检查。

### M4—M5：从出图到业务正确

- 同步处理 vertex/index、shader 特化、纹理格式、采样器、混合、深度/模板、viewport/scissor、颜色空间及窗口纹理轮转。
- 当前 Eden 的 compositor 指纹和场景补丁不直接作为新后端的分类依据。按 D3 源程序、附件和实际 render pass 建立可复核的场景/UI 识别；不确定的 draw 保持原路径。
- 保留当前宽屏的 UI、取景和菜单相机行为；原生清晰基线先通过，降分辨率/VRS 随 T3 单独验收。
- 先完成第 7 节功能，再进入正式功耗比较。世界有像素、present 计数增长或输入提交成功都不构成业务完成。

## 6. T1—T5 的实现与专项验收

### T1：精确写入跟踪与扫描

实施：

1. 先验证已有 CpuWriteTracker 元数据/快照拆分与减少 worker 唤醒候选，保留普通全扫描回退。
2. 以资源写入范围/子资源通知减少需要检查的集合；仍须覆盖没有显式通知的 guest CPU 写入。
3. 依页面大小、冷热分布和动态写入密度，试验保护粒度及连续范围合并；避免高频动态页反复 mprotect/fault。不能直接把所有池按同一粗粒度保护。
4. 保留精确 memcmp/memcpy、审计和 watch-miss 计数；任何加速不得依赖遗漏真实写入。
5. 统计比较字节、变化页、审计次数、fault、mprotect、worker 唤醒、扫描时间和每游戏帧的总成本；审计点单样本不代表常态。

专项验收：

- 现有 tracker、布防竞争、内存区域、stack/HID 测试及相关新边界测试通过；ARM64 程序须真正执行并记录退出码。
- 测试场景审计的 watch-miss 为 0，画面/数据无陈旧；零 miss 仍不能单独替代功能验收。
- 工程目标为同负荷扫描总耗时至少降低 30%，或确认内存比较量明显减少；指标须按扫描频率和游戏帧数归一化，不能靠少出帧降低总量。
- 默认启用仍须通过第 8 节功耗与帧时对照。已有 write-watch 曾出现 CPU 降而 FPS 降，扫描变快不能单独判定通过。

### T2：ADPF 调度提示

实施：

1. 接入标准 APerformanceHint 接口，按能力检查；不支持时正常回退，不依赖 root、包名伪装或锁大核。
2. 使用真正执行关键渲染工作的 TID 建会话。工作序号与帧匹配，排除队列空闲、主动限帧和 acquire/显示节拍等待；驱动/GPU 依赖等待另行标记，不能把整段 present 墙钟都当 CPU 工作量。
3. 目标时长跟随实际选定帧率；暂停、Surface 消失、线程更换和退出时清理，丢弃未匹配/过期样本。
4. 分别在 Eden 和 NVN 后端试验；T1 状态先固定，避免两项一起开导致归因不明。

专项验收：

- 每个会话的 TID、目标时长、样本序号正确；没有 0/负数/旧帧样本，线程重建后不会向旧会话继续上报。
- 前后台与 Surface 循环后无会话泄漏或后台持续提示。
- 采样验证调度等待、关键线程工作时间、频率和最终帧时。频率高/低本身不作通过条件。
- 同帧率功耗降低超过第 8 节门槛才记节能；若只改善帧时而增加功耗，单独记录为性能结果，不记为功耗达标。

### T3：GPU 像素与带宽

实施分两层，先做不改变画质的资源/复制优化，再试画质折中：

1. 统计附件 load/store、render-target 切换、blit/copy/resolve 与采样路径；只消除已经证明不被后续读取的保存/复制。Mali 的片上 tile 利用要结合实际 pass 结构验证。
2. 为 3D 与 UI 分别确认附件尺寸、viewport/scissor、crop、深度和采样坐标。每个缩放档单独出配置回执；最终截图尺寸不代表内部渲染尺寸。
3. 将现有场景线性缩放作为独立候选，原生 UI 保持不变。已有 EASU/RCAS 世界全黑问题未通过前，不作为可用省电档。
4. 对实际加载的驱动重新查询并启用 VRS 能力，先试受控 2×1/1×2；排除有副作用、互锁、逐样本语义及无法确认正确性的 shader。UI/文字/最终合成显式恢复 1×1。
5. 需要时用诊断 GPU timestamp 或计数器定位真实成本。host 的 gpu_wait_us 不等于 GPU 执行时间；逻辑复制字节也不冒充物理总线流量。

专项验收：

- 城镇、移动、物品栏、阴影、透明、粒子、地面效果和密集战斗中，无黑场、闪烁、漏层、错误深度/裁剪；文字与 UI 不被误缩。
- 每个档位实际场景/UI 尺寸、着色率和 GPU/复制成本可复核；按场景分类失败时使用正确基线。
- 无画质变化的带宽优化按同画质 A/B；缩放/VRS 明确标为不同画质档，不混入“同画质节电”结论。默认档仍须满足既有清晰度要求和第 7、8 节。

### T4：背压、批量提交和复用

实施：

1. 先用诊断确定重复分配、descriptor 更新、上传、全局等待以及过量在途工作的来源；Eden 已有的机制不重复实现。
2. 对任务数、在途帧和待处理内存设明确上限；试验满足吞吐的最小预算，记录高水位、等待及输入延迟，不让队列无限增长。
3. 按 fence/资源寿命复用命令、临时缓冲、上传空间和 descriptor；完整比较绑定 key，资源销毁/重用时更新 generation。
4. 扩容失败明确返回错误；绝不能把容量不足的旧缓冲按新请求大小使用。复用缓存必须有容量和回收策略。
5. 合并提交不得跨越要求立即可见的同步边界。当前 present 中的 WaitForComposite 不能因为“等待耗时”就直接删除。

专项验收：

- 队列和内存受控，压力/超时/退出可结束，无 use-after-free、旧绑定和死锁。
- 已定位的稳态热点以减少至少 50% 的冗余更新，或减少至少 80% 的重复临时分配作为工程目标；本来没有这类热点则跳过该子项，不人为制造优化成果。
- 输入到可观察动作的 P95 延迟，相对基线增加不超过一个 60 Hz 显示周期；测量链不可用时该项标未测。
- 总工作量、CPU/驱动时间和功耗按真实帧数归一化；正式启用仍须过共同门槛，不能只凭 vkQueueSubmit 次数减少判定节能。

### T5：暗黑 3 shader 与管线预热

实施：

1. 把实际 Vulkan profile、D3 源 shader 和特化组合送入 M1/M4 选定的编译链。一次静态抽取数量不能当作所有职业、地图和特效覆盖。
2. 缓存键包含游戏 BuildID、源 shader/特化、翻译器与接口版本、设备/驱动 profile。Vulkan pipeline cache 同时核对设备 cache UUID；Android 与 Windows 的设备产物不直接互拷。
3. 优先离线生成可验证 shader，再在加载期预热常见 pipeline。额外启动预热预算初定 ≤5 秒，超出则分批或保留按需编译，不在后台无限占核。
4. 冷缓存、暖缓存、损坏/旧缓存、首次新特效分别测试；写盘原子提交，缓存损坏时可重建，不能跳 draw 或黑场。

专项验收：

- 已收集的固定路径，在暖缓存重复 3 轮时没有重复编译同一组合；首次未覆盖组合能正确编译和缓存。
- 缓存失效和错误恢复可复现；系统/驱动或编译器更新后不会继续使用不匹配产物。
- 冷缓存路径中 >50 ms 的编译相关卡顿次数，工程目标降低至少 30%；若基线没有相关卡顿，报告事实而不编造比例。
- 冷启动时间、加载时间和编译能量单独记录。暖缓存持续功耗不劣化，不能把首次编译消失等同于持续节电。

## 8. 帧率、功耗和实验协议

本节数值为计划采用的工程验收门槛，不是已测成绩。M0 在首次正式对照前冻结；如需调整，应更新协议并说明原因，旧数据保留原口径，不事后为过线改门槛。

### 8.1 场景与控制变量

- 固定游戏版本/BuildID、存档快照、角色等级/装备/技能、地图、路线和敌人负荷。随机场景无法匹配时分组统计，不伪称严格同场景。
- 固定实际场景/UI 尺寸、宽高比、帧目标、驱动及其加载路径、屏幕亮度和实际刷新模式。关闭自动亮度及会改变负荷的 OEM 插帧/注入；配置回执记录实际生效值。
- 主基线使用正确的原生画面，不以黑场、错误特效、过场或菜单刷帧作性能基线。T3 的不同画质档单独列结果。
- 同设备配对窗口起始电池温度 ≤35°C、相差 ≤1°C；记录环境温度、电量和热状态。窗口中的真实温升不能通过截掉后半程隐藏；触发采集器退出条件则记录未完成。
- 每个后端独立预热缓存。预热结束后停止游戏或按协议准备测试，不在编译、分析、等待或冷却期间保持游戏运行。

### 8.2 诊断、短窗与长窗

1. **诊断窗口**：验证层、trace、帧日志、回读按需要单独开，定位问题；不参与节电结论。
2. **噪声基线**：同一候选、同一设置至少 3 个 180 秒 A/A 窗口，记录功耗和帧时自然范围。若负荷或环境持续漂移，先解决漂移。
3. **单项对照**：至少 3 组串行 A-before / B / A-after，每个有效窗口 180 秒；轮间停止、确认进程退出并恢复场景和热条件。B 一次只改变一个因素。
4. **组合对照**：单项通过后比较“全部关闭、逐项加入、最终组合、关键项关闭”的结果，检查相互作用；不同优化的节电百分比不得简单相加。
5. **最终窗口**：最终配置至少 3 个独立、完整的 15 分钟持续战斗窗口。过场/加载另测，不拼接最好的片段；游戏中的卡顿和后段热降频必须纳入。

### 8.3 计量有效性

每个窗口开始前检查 APK/SO、PID、进程启动 ticks、boot ID、配置和驱动，结束时复核。任一身份变化，当前窗口不作同一构建比较。全部外部供电必须为 false，USB 充电和仅有电池净电流的数据不计算“整机省电”。

将电压、电流统一为 V/A，放电电流按已确认的接口符号换算，以设备 CLOCK_MONOTONIC 时间作梯形积分：平均功率 = 电能积分 / 有效窗口时长；不得取绝对值掩盖充电或符号错误。保留单位、原始读数和解析失败。

电量采样有效率要求 ≥90%，最大连续缺口不超过 3 个采样周期；超出则保留原始数据并判该功耗窗口无效，不能任意补零/补平均值。电量计数器可用且分辨率足够时，与电流积分交叉核对；明显不一致必须先查单位/接口/时间窗。

帧率区分 guest/composite、渲染提交和真实上屏。正式“原生 60 FPS”必须有可关联的实际显示帧证据；屏幕 120 Hz 重复帧、OEM 插帧及 composite 计数不代替独立游戏帧。显示跟踪不可用时只报告已测的提交/合成帧率，最终上屏项保持未验。

### 8.4 单项节能的共同门槛

设 P_A 为当前配对的两个 A 窗口均值，P_B 为 B 的均值；噪声底 N_P 取下列较大者：同条件 A/A 功耗极差、0.10 W、A/A 中位功耗的 2%。

只有重复对照显示 P_A − P_B 同时超过 N_P 和 P_A 的 5%，并且没有画面/业务退步，才记为明确节电收益。未超过门槛记“收益未证实”，不等于证明无效果；帧时改善和冷编译改善可分别记录。

与 A 相比，B 的平均上屏 FPS 降幅不得超过 max(0.5 FPS, 1%)；帧间隔 P95 增量不得超过 max(1 ms, A 的 5%)。这只是单项不回退门槛，不能代替最终 60 FPS 目标。低画质档的收益单列，不能混成同画质收益。

### 8.5 最终 Android 交付门槛

| 项目 | 必须满足的条件 |
| --- | --- |
| 画面与功能 | 第 7 节必需用例通过；无黑场、错误层次、陈旧资源、数据损坏及新增崩溃 |
| 原生上屏帧率 | 软件目标保持 60 FPS；每个 15 分钟有效窗口平均 ≥59.5 FPS，任意完整 10 秒子窗 ≥59.0 FPS；无插帧/重复帧冒充游戏帧，实际值不四舍五入成 60 |
| 帧间隔 | 上屏间隔 P95 ≤20 ms、P99 ≤33.4 ms；>50 ms 间隔不超过平均每分钟 1 次，战斗中的停顿不被剔除 |
| 持续性 | 每窗最后 5 分钟仍满足帧率门槛，不能只用冷机前段达标 |
| 整机功耗 | 3 个有效 15 分钟窗口各自平均 ≤4.5 W；对应最后 5 分钟也各自 ≤4.5 W；同时满足帧率和画质 |
| 稳定与清理 | 无 native fault、GPU hang、超时或采样身份异常；测试/退出后确认游戏进程已停止 |
| 可交付性 | 可重建、来源与许可完整；安装身份/配置/驱动可追溯；原签名和数据保留，回退包验证可用 |

满足平均功耗但掉帧、牺牲未声明画质、靠黑场减少 GPU 负荷、只有 USB 下 CPU 降低，均不记最终完成。未同时过线的结果按“功能候选”“性能候选”或“节能候选”记录。

## 9. 工具、证据与回退

### 9.1 现有工具和相关测试

- 构建入口：android/tools/build_android_profile.py；使用保留 guest 和匹配的 keystore，具体命令遵循 [BUILD](BUILD.md)。新增后端参数实现前不得把建议参数写成现成命令。
- 帧时/身份：capture_android_runtime.py、summarize_android_runtime.py；必须传对应 manifest，使用设备 CLOCK_MONOTONIC，排除历史 PID 和窗口外日志。
- 拔线功耗：capture_android_battery.sh、collect_android_battery.py；设备本地采集器保留退出清理，即使无线 ADB 中断也有停止路径。
- 现有测试重点：test_cpu_write_tracker.cpp、test_cpu_write_watch_arming.cpp、test_memory_regions.c、test_stack_memory.c、test_hid_memory.c、test_guest_tls.c/.S、test_syncpoint_wait.cpp、test_frame_pacing.cpp、test_scene_region.cpp、PresentationPolicyTest.java。按改动补有意义的边界测试；编译成功不等于 ARM64 实机执行通过。
- Python 离线回归入口为 python -I -m unittest discover -s android/tests -p 'test_*.py' -v；不以离线全绿替代真实图形与业务验收。

### 9.2 每个有效测试窗口的最低证据

统一放在 out/android/power-roadmap/ 下，每窗一个新目录，至少包含：

- manifest：用例、后端/T1—T5 开关、源码与补丁、APK/SO/guest/内容身份、签名证书摘要、配置、驱动、PID/启动 ticks/boot ID、场景、亮度/刷新/温度/供电和采样时钟。
- 原始电量采样、原始帧事件、日志与逐命令审计；所用诊断及其是否进入功耗窗口明确记录。
- 功能窗口的截图/动作 before-after；性能窗口保留定位到相同用例的场景证据，但关闭持续录像和像素回读。
- analysis：有效性、功率积分、真实帧率及分位数、后 5 分钟、噪声与配对差值、异常、通过/失败/未测结论。

游戏资源、密钥、签名私钥、存档及唯一输入只放 local/，不进入证据目录或源码 Git。只有汇总、没有原始身份与时间窗的数据不能作为验收依据。

### 9.3 回退与停止条件

1. 每项变更独立提交/补丁和开关，记录对应 APK；保留能够复现的正确画面基线和匹配签名。
2. 出现错图、数据错误、死锁、GPU hang 或 native fault，停止该窗口、保存证据、尝试 force-stop 并核对退出；修复后从相关用例重新验证。
3. ADB 中断时区分传输异常、系统 cleaner 和 native fault；无法核对退出就明确记录，下一轮前必须重新确认上一轮已停止。
4. 后端只在冷启动切换；T1/T2 等热切换只有在接口明确实现、状态已稳定且不会跨窗污染时才用于诊断。
5. 普通配置不默认启用未验候选。组合失败时先回到已验基线，再逐项定位，不同时换驱动、降尺寸和改同步。

## 10. Windows 可复用部分与独立路线

### 10.1 可以收益，但不是自动继承安卓结果

Windows 当前使用独立的 ScarletNX 构建。S2Arm NVN→Vulkan 可能减少其图形处理开销；资源变化跟踪、批处理和缓存方法也可借鉴。图形迁移不自动改变 Windows 的 CPU 执行路径，安卓的 ARM64/TLS/汇编、信号和 Surface 接口不能原样搬过去。

| 工作 | 可以共享的部分 | Windows 必须单独处理的部分 |
| --- | --- | --- |
| M 直连后端 | D3 NVN 语义、命令/资源模型、部分 Vulkan 逻辑 | ScarletNX 接入、guest 调用约定、线程/异常、分配与 Win32/Vulkan 呈现 |
| T1 写跟踪 | 资源/子资源代次、精确变化语义和测试用例 | Windows 内存保护、异常分发、映射/分配粒度和宿主一致性接口 |
| T2 调度 | 按工作量和帧预算管理关键线程的方法 | ADPF 不适用 Windows；是否需要平台线程调度优化另行采样，不能机械替换成最高优先级 |
| T3 GPU 负荷 | 场景/UI 分层和冗余拷贝分析 | Intel Arc 等实际显卡的能力与驱动；VRS 不继承 Mali 配置；现有 Windows FSR/分层补丁重新适配 |
| T4 队列与复用 | 背压、完整缓存 key、generation 和批处理语义 | 宿主队列、资源回收、输入延迟和 Windows 显示链路 |
| T5 shader | D3 源程序、特化和预热覆盖清单、部分工具 | 按 Windows 设备/profile 重编译；驱动 pipeline cache 与 Android 分开 |

Windows 先复用已证明有价值的纯逻辑/数据模块。存在 POSIX/Android 依赖的模块先审计和适配，不为通用平台框架扩大范围；公共部分仍只服务暗黑 3。

### 10.2 Windows 的实施出口

1. W0：单独激活 windows/source/ScarletNX-src 的 Serena 项目，定位实际 GPU、内存、shader、窗口和调用桥；核对当前补丁链及运行时身份，建立原生 60 FPS 的同场景基线。
2. W1：确定可共享源码闭包，把平台绑定放在 Windows 适配处。Windows 修改通过 windows/patches/base.json 的链重放，不只改被主仓库忽略的源码树，也不复用 Android 的 hook 偏移。
3. W2：先过画面和第 7 节适用业务用例，再复测原生 KBM：移动/世界点击、目标交互、攻击、技能、UI、菜单及快捷键。SDL 接受事件不等于业务完成。
4. W3：用 Windows 实际上屏帧时和独立功耗口径做同条件 A/B/A；显示刷新率固定，现有 120 Hz 呈现问题分开控制，不能将驱动/显示模式变化计作移植收益。

Windows 测试统一使用 Launch-Background.ps1：1024×576、位置 (40,40)、后台非置顶、SWP_NOACTIVATE。不拉前台、不用真实光标/SendInput；每次按完整路径、启动时间和 SHA-256 同时确认进程。功耗对照按实际取景和内部尺寸匹配，窗口外观相同不代表负荷一致。

Windows 节能验收采用同原生帧率、同画质下超过 A/A 噪声的相对整机功耗降低；测量仪器、取样和阈值在 W0 单独冻结。仅 CPU package 或 GPU 功率不代表整机，也不能把包含重叠域的读数直接相加。Android ≤4.5 W 不作为 Windows 门槛；缺 Windows 实测时只写“可复用/待验证”。

Windows 结果统一更新 [Windows STATUS](../../windows/docs/STATUS.md) 和 [当前交接](../../windows/docs/HANDOFF-20261104-CURRENT.md)，跨平台概要更新 [总 STATUS](../../docs/STATUS.md)，不将安卓成绩直接标到 Windows。

## 11. 完成定义

文档、代码可编译、清屏成功、进世界、功能回归、单项节电、最终持续目标分别记录。M1—M5 完成只说明移植逐步可用；只有 M7 的功能、帧时、功耗、持续性和可回退性同时通过，才把 Android 路线记为最终完成。

若 NVN 直连没有在目标设备显示优势，应保留测量与原因，使用已验证有效的 T1—T5 改动继续改善当前路径；路线选择按暗黑 3 的实际收益决定，不以迁入上游代码数量作为成果。
