# Android 当前状态与验收

更新：2026-11-11。本文件只记录 Android 路径的已验收范围与剩余工作；构建见 [BUILD.md](BUILD.md)，架构见 [ARCHITECTURE.md](ARCHITECTURE.md)，Windows 见 [Windows 状态](../../windows/docs/STATUS.md)。

Android 路径通过 Horizon 兼容层与 Eden GPU 栈执行原始 ARM64 guest。正常基线为系统 Vulkan、1.0×、write-watch 关闭。

**S2Arm 路线评估（2026-11-11）**：已核对留存 APK `fa6ae5a5…` 与构建账本一致，截图显示暗黑 3 世界场景/HUD，用户明确确认当时使用 NVN 直连。该路径是可复用的 Android NVN→Vulkan 候选；尚无同机同条件帧率/功耗对照，不能写成优于现方案或已达到 60 FPS / ≤4.5 W。当前建议先验证直连包，再按暗黑 3 实际需要适配图形模块；本轮未迁入运行代码、未开启新的游戏测试窗口。独立节能候选优先验证扫描/写跟踪与 ADPF，其次按采样验证队列/缓存复用、着色器预热、场景像素/带宽与菜单帧率策略，均未证明节电。源码入口、现存证据与迁移边界见 [架构评估](ARCHITECTURE.md#s2arm-图形路线评估2026-11-11)。

**当前功耗优化实验（2026-11-10）**：validation 已导入 Windows 70 级角色，设备安装 APK 为 `7439ED1A…`，保留自定义 Mali 驱动；原生 1× 城镇场景/文字获用户确认正常，修正后的 EASU+RCAS 世界画面仍黑。一次请求场景 0.75× 线性、上限 60 的拔线窗口测得整机电池侧均值 **6.674 W**（118.45 秒、57 点，33.1–33.4°C）、原生 composite **45.94 FPS**；实际场景/上屏仍待复核，未达到稳定 60 或当前 **≤4.5 W** 目标。0.625×/30 候选被 cleaner force-stop，未形成有效功耗数据。已准备缓存元数据拆分/减少扫描线程唤醒候选，GPU 库、宿主、签名 APK 和 ARM64 测试程序仅完成离线构建，未安装或执行新测试。VRS 系统能力与后端接入点已找到，尚未启用。详情和证据见 [Android 构建说明](BUILD.md) 与 [架构说明](ARCHITECTURE.md)。测试结束或失败必须关闭游戏；用户暂时带走手机期间不连接、不启动游戏。

OEM 游戏助手“提升帧率”可切换，运行配置可见 `45→90`、90Hz 请求。**真实生成输出、延迟与伪影尚未验收。** 普通 HOME 返回后曾读到关闭态，随后 ADB 断开，尚未确认自动恢复。界面选中或 90Hz 面板模式不能作为实测 AI 90 FPS。

2026-11-10 已安装并实机验收 `com.miHoYo.Yuanshen` 场景分层修复：场景实际输入为 `1200×540`，只对匹配的场景附件使用 0.75×；合成时通过 `vkCmdBlitImage` 线性放大到 `2000×900`，UI、文字和虚拟手柄仍按 `2000×900` 绘制。此前 vivo GameLib VSR 会让宿主 render pass 和描述符写回路径在 Mali 驱动中崩溃，或令实验 FSR 输出全黑；当前默认因此使用传输回写，不做全帧超分。最终精确安装构建已核对标题画面、片头 CG 和虚拟手柄，连续跑到 `draw=2100`，无 SIGSEGV、Vulkan validation 或 VSR 崩溃；同一场景回写路径的清理前构建另已进入城镇并跑到 `draw=7200`。安装 APK 与本地产物逐字节一致，SHA-256 为 `53D8E825D6E3E48EE31F210A01D68A7CBE409338699718281EC6D0E9E64DE99C`；证据在 `out/android/performance/genshin-20261110/`。真实 EASU/RCAS 在该设备的画质、长时性能和功耗仍未验收。

本次设备实际报告为 V2405A、MT6991、API 37，保留当前自定义 Mali r49p1 驱动。1.0× 同城镇静置、同 PID 32720 的四个 120 秒窗口采用“事件等待→旧 1ms 轮询→事件等待→旧轮询”交替对照，各窗口的诊断模式一致：

| 同步方式 | 原生 composite 报告 FPS 加权均值 | 帧间隔 P50 | 呈现回调线程 CPU 均值 | 整进程 CPU |
| --- | --- | --- | --- | --- |
| 事件等待，两轮 | 39.901 / 40.053 | 24.956 / 24.905ms | 0.126 / 0.126ms | 253.41 / 254.89% |
| 旧轮询，两轮 | 40.066 / 40.136 | 24.923 / 24.862ms | 0.258 / 0.259ms | 252.25 / 253.27% |

事件等待减少回调线程轮询开销，当前数据未显示城镇帧率或整进程 CPU 的明显改善。两种方式都未达到原生 60fps；静置 composite 统计也不能替代持续战斗及实际上屏验收。温度 40.7–40.9°C、全程 USB 供电，不能报告放电功耗或节电比例。诊断窗口已按独立时钟 helper 的 `CLOCK_MONOTONIC`、PID、启动 ticks 与 APK SHA-256 过滤；含 suspend 的 `/proc/uptime` 与单调时钟在本机相差约 627.5 秒，不能混用。原始与汇总证据在 `out/android/performance/syncwait-ab/`。

缓存扫描仍是明确的成本来源：上述窗口每轮约 3.3 万个 4KB 页面、约 34–40 个变化页，抽样扫描耗时中位约 9–10ms；扫描日志每 256 轮抽样，不能视为逐帧全量统计。CPU 写入跟踪仍需单独完成集成与一致性验收，不能通过跳过扫描或不精确 hash 改善帧率。

后续诊断增加了完整扫描批次统计，避免 write-watch 的 256 轮全量审计与单点日志同周期造成偏样。`9BF17654…` 普通配置的独立冷启动城镇窗口为约 50.761 composite fps，5888 轮扫描的加权均值 8.736ms；相邻 120 秒原生 SurfaceView 采样确认时间戳与 `CLOCK_MONOTONIC` 一致，已呈现间隔均值约 19.778ms、P95 33.282ms，仍未达到持续 60fps。它与前述同进程 40fps 对照不是同一进程/窗口，不能把数值差异归为代码优化收益。证据在 `out/android/performance/cache-watch-ab/ordinary-01/` 与 `ordinary-surface-01/`。

一次强制全扫描启动（PID16703，write-faults=0）在首帧附近因 `overlapping regions` 退出。已发现内存 SVC 对共享区域表的并发重建/排序和 QueryMemory 缺少同步；独立 ARM64 回归在旧代码复现重叠/查询空隙错误，新增串行化后连续三轮各 768 次并发映射/查询通过，原 stack/HID 内存测试也通过。`DD673FFE…` 已在强制全扫描模式冷启动进入城镇（PID21658）；第二次启动未完成验证即按测试安排中止，不能记为通过或失败。

另一个独立的首次布防竞态已通过真实写故障测试复现：保护已生效但 `Active` 尚未发布时，旧处理器错误拒绝故障（退出99），新增等待 `Busy` 发布后精确恢复（退出0），完整 tracker 回归也通过。包含两处修复的 `736F33B0…` 已核对安装哈希并冷启动进入城镇（PID24162，强制全扫描模式），证据在 `out/android/performance/memory-regions/` 与 `watch-arming-install/`。这些结果不证明已修复所有启动失败。

同 PID24162、同城镇、同 1.0×/驱动的四轮各 120 秒对照已完成：全扫描两轮约 41.237 / 48.593 composite fps，write-watch 两轮约 38.153 / 38.195。扫描批次加权均值从 9.533 / 8.974ms 降至 2.477 / 2.452ms，整进程 CPU 从 260.7 / 282.6% 降至约 213.8 / 213.9%，但 composite 等待从约 4.65 / 2.40ms 升到约 9.73 / 9.71ms。窗口内抽样审计的 watch-misses 均为 0，观测写故障累计增量约 4.7 万次/轮。精确原生 SurfaceView 呈现数据也显示 watch 的平均间隔约 26.2ms、P50 约 33.2ms，未达到 60fps，因此不能将目前 write-watch 作为性能达标方案。设备已恢复强制全扫描，后续串行采集了全扫描/跟踪/全扫描的调度、频率和 syscall trace；尚未确定新增等待的根因。对照在 `out/android/performance/cache-watch-ab/comparison.json`，trace 在 `cache-watch-scheduler/`。仍为 USB 供电，不报告节电比例。
